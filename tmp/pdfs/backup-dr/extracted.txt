02 | OBJECTIVES AND IMPACT
Definitions and measurement rules
Use recoverable business state, not backup-job success, as the measure.
Term
NUERS operating interpretation
RTO target
Approved maximum time from the actual start of business-service
interruption to validated restoration of the agreed minimum service.
Observed recovery time
T(recovered and accepted) minus T(outage began). Record declaration
delay separately; do not restart the clock when an engineer begins work.
RPO target
Approved maximum tolerable age of lost committed data at the
interruption boundary. Define it for all dependent stores, not only the
database.
Observed data-loss interval
C(last acknowledged source commit) minus C(latest contiguous
recovered commit). Also count lost records and financial value.
Recovery point age
T(outage) minus C(recovered). Report alongside commit gap, especially
during quiet periods when no new data exists.
MTPD / business tolerance
Maximum tolerable period of disruption. Proposed critical-service
planning ceiling: 8 hours, requiring service-owner approval.
Recovery complete
Authorized users can access the intended data and services; integrity
and financial checks pass; delivery ambiguity is reconciled; monitoring is
active.
Use UTC timestamps with precision and a monotonic elapsed timer when available. Preserve
the timezone, clock source and uncertainty. The lab uses observed transaction-commit markers
rather than database log sequence numbers; production tests need engine-native positions and
business acknowledgments.
Planning reference: NIST SP 800-34 Rev. 1 describes contingency planning, business impact analysis and
recovery planning. The specific targets and NUERS procedures in this document are proposed local policy.

03 | OWNERSHIP AND SAFEGUARDS
Recovery safeguards and release
gates
Preserve one authoritative writer and one verifiable business history.
Fence before restore: disable old-site database writes and transaction intake; pause
schedulers and delivery workers. DNS changes alone do not fence a writer.
Restore into an empty target: never overwrite the only surviving copy. Preserve incident
snapshots and immutable evidence before remediation.
Keep external delivery paused: mail, merchant callbacks and government transmission
must not replay automatically from restored queues.
Protect identities and secrets: keep tenant scope, Live/Sandbox separation, MFA, API
restrictions and key version associations intact.
Reconcile money and identifiers: validate wallet chains, accepted event IDs, invoice
numbering and receipts before enabling new writes.
Release on evidence: record test results, known losses, business acceptance and rollback
criteria; never label an untested backup as recoverable.
Stop conditions
Stop recovery release if a checksum fails, a required key cannot be recovered, audit or wallet
integrity fails, source/outbox state is ambiguous, the selected recovery point is incomplete, or
the old writer cannot be fenced. Escalate to the incident commander and preserve the failed
attempt.
CODE BASELINE: the NUERS backup dashboard records requests, evidence and independent reviews. It
does not itself perform infrastructure backup, live restore or failover. The operator must execute the
approved procedure outside that evidence workflow.

05 | BACKUP PROCEDURES
BP-01 | Prepare and capture a
backup
Operator checklist - consistent state first, copy second.
Step
Procedure and evidence
1. Authorize
Record job ID, environment, tenant/all-tenant scope, release, operator and
approved destination. Verify that capacity and retention policies are active.
2. Check
dependencies
Verify key references, destination access, synchronized clocks, database
health and previous successful backup. Alert on missing prerequisites.
3. Choose
consistency method
Use the deployed engine's supported consistent snapshot plus native log
position. For file-based lab SQLite use its Backup API. Do not copy a changing
database file blindly.
4. Bind object
versions
Capture a manifest of private object versions associated with the database
point. Quiesce writes if no proven cross-store consistency method exists.
5. Capture database
and logs
Record snapshot/transaction position, start/end time, row-level control totals
and encryption metadata. Confirm the expected backup format and engine
compatibility.
6. Capture dependent
assets
Copy required object versions, templates, release/dependency manifests and
configuration references. Exclude live secrets from ordinary artifacts.
7. Confirm completion
Verify that the process succeeded, files are non-empty, bytes/hash match and
the set is complete. Treat partial completion as failed.
When quiescing, announce the maintenance window, reject or safely queue new intake, wait for
in-flight commits, pause mutating jobs, take the consistency point and record the write-resume
time. An outage caused by backup quiescing belongs in service monitoring.
The SQLite Backup API provides a consistent database snapshot. Its use in the lab does not validate a
production MySQL/MariaDB backup procedure; the deployed engine/version needs its own restore test. [R3]

05 | BACKUP PROCEDURES
BP-02 | Encrypt, transfer and verify
A backup is usable only after integrity and recoverability are established.
Step
Procedure and acceptance evidence
1. Encrypt
Use the approved backup encryption mechanism and versioned key reference.
Ensure application-encrypted objects remain encrypted in transit and at rest.
2. Authenticate
manifest
List backup ID, environment, release, engine/version, capture position, object
versions, byte counts, SHA-256 values and key references. Sign/authenticate
the manifest with separate restricted custody.
3. Transfer
Upload through an approved encrypted transport to an independently
administered destination. Record destination object/version identifiers and
provider completion evidence.
4. Read back
Verify hashes from the destination, not just the local staging file. Confirm
retention, versioning, access controls and expected storage region.
5. Lock and isolate
Apply the approved retention lock/offline process. Confirm that ordinary
application credentials cannot remove protected copies.
6. Restore sample
Restore a representative subset into an isolated target; decrypt and inspect
private files and verify ledger/identity links. Capture measured results.
7. Register evidence
Record backup and test evidence in the NUERS governance workflow, then
obtain independent review. Preserve failed attempts and remediation actions.
Do not mark a backup successful when transfer, verification, key recovery or required assets
are missing. Route failures to an accountable operator, retry within the recovery-point budget,
and escalate when the latest usable point approaches the RPO target.
AWS Object Lock is a possible future WORM control for versioned objects. Governance bypass permissions
and retention mode must be evaluated; no such control was configured or tested in this exercise. [R4]

05 | BACKUP PROCEDURES
Encryption and recovery key custody
A recoverable database with unrecoverable keys is still a failed recovery.
CODE BASELINE: private documents use authenticated Laravel encryption in bounded frames
and verify plaintext size and SHA-256 before exposing contents. Wallet and audit chains provide
integrity checks. These application controls do not prove volume encryption, offsite backup
encryption or cloud key-service availability.
Control
Proposed operating requirement
Key register
Map each backup and encrypted dataset to required application, backup
and signing key versions. Record owner, activation, retirement and
recovery location.
Custody separation
Keep key escrow separate from backup data and from the same primary
host/account failure domain. Use a vault or equivalent approved control.
Recovery access
Require named custodians, strong MFA and a second-person approval for
emergency key release. Test alternate access without relying on the failed
identity service.
Rotation
Retain prior decrypting keys for as long as corresponding data/backups
must remain readable. Validate restore before retiring a version.
Compromise
Preserve evidence; rebuild a clean target; rotate exposed credentials in an
ordered plan. Do not rotate the encryption key blindly and render retained
data unreadable.
Evidence
Record key version and custody approval, never the key value. Store
recovery secrets outside this document and ordinary test exports.
LAB LIMIT: the drill read separate lab-only keys from a restricted local escrow file. This proves the tested
decryption path, not dual-person custody, hardware protection or recovery after workstation loss.

Recovery sequence and control
gates
D03 - Move forward only when each preceding gate has evidence.
 1 Declare + fence
Confirm outage; stop all writers
 2 Restore clean point
Database, objects, keys and exact release
 3 Validate + reconcile
Ledger, audit, sequence and unknown sends
 4 Authorize + reopen
One writer; controlled worker restart
 5 Observe + fail back
Measure recovery; rebuild standby safely
Each stage has a named operator, timestamp, validation output and release authority. Preserve failed attempts
as part of the incident record.
Traffic switching is late in the sequence. Restore and reconcile before accepting new financial
events. Prevent split-brain by disabling the old writer at the database/network/service layer and
checking that no scheduled worker continues to mutate state.
Recovery time includes the time needed to detect the interruption, obtain access, select data,
transfer, restore, validate and accept service. A separate component timing can aid diagnosis
but does not replace the full-service measure.
Live BIR delivery remains governed by its own approved connection, permits and authentic
acknowledgment controls. Recovery must preserve those gates and cannot substitute an internal success
record for an external acknowledgment.

06 | DISASTER RECOVERY RUNBOOKS
DR-02 | Restore to an isolated target
Database, objects and release must describe the same recovery point.
Stage
Required action / stop condition
1. Establish clean target
Provision approved OS/runtime/database versions and storage. Verify
network restrictions, time, disk capacity and administrative access. Keep
user traffic and outbound delivery blocked.
2. Select backup set
Confirm clean point, manifest authentication, hashes, engine version,
required logs, object versions and decrypting keys. Stop if any required item
is absent.
3. Restore database
Use the engine-supported restore procedure. Replay only the verified
continuous log range up to the selected point. Record final LSN/GTID/binlog
or equivalent marker.
4. Restore objects
Restore corresponding private object versions, file metadata and receipt
branding. Verify existence, decryptability, size and plaintext hash.
5. Restore application
Deploy the exact compatible release and dependencies. Restore approved
configuration and key versions. Do not automatically run forward migrations
against the only recovered copy.
6. Isolate workers
Pause schedulers, customer mail, callbacks, BIR jobs and automatic retries.
Capture queue/lease status before changing it.
7. Validate state
Run database integrity, business control totals, ledger and audit checks,
source identity checks and scoped read-only UI/API acceptance.
Restore production snapshots only into an approved restricted environment. Use masking for
non-production development, but retain sufficient protected evidence for an authorized recovery
validation. The lab contains synthetic data only.

Additional controls
