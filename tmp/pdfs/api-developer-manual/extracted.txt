01 / ONBOARDING
Prepare a merchant connection
Contract: NUERS-ingestion-1 | Verified source snapshot: 18 October 2026
NUERS | ERP / POS / ecommerce integration | 18 October 2026
3
1. Register the business and complete its document review. The account must be active before managing keys or
submitting new financial events.
2. Confirm the registered taxpayer identity and effective VAT registration in Business Profile. No separate merchant
Branches / Terminals setup is required.
3. Open Merchant > API Integration > Generate New API Key. Enter only a descriptive name, such as ERP
Production. The registered Merchant Admin must have completed MFA for the current login.
4. Copy the key once into a backend secret manager. Edit Key Policy to restrict public egress IPs and reduce
permissions where appropriate.
5. Call the authenticated wallet endpoint to verify connectivity and read the assigned merchant_id and branch_code.
Store that branch_code in the connector configuration. Never invent or guess a code.
6. For copies, obtain the administrator-reviewed source_profile_id for the exact source_system, registered location,
original seller and original issue period.
7. Fund the NUERS wallet as required by current pricing. Validate synthetic payloads, complete isolated staging
tests, then perform an authorized pilot and reconcile it.
Assigned identity remains strict
Removing the branch page simplifies setup; it does not remove branch identity from transaction data. Each
event must still carry the exact five-digit branch_code assigned to its key. Additional registered locations need
administrator coordination; a name-only key does not grant cross-location access.
A missing or ambiguous registration identity can block key generation with HTTP 422. Correct the business registration through the
administrator review process. Existing inactive location records are not automatically reactivated.

Source-profile matching
The profile must belong to the authenticated merchant and match both source_system and branch_code. Its
inclusive valid_from / valid_until interval must contain occurred_at. The reviewed seller snapshot supplies effective
VAT registration for captured originals. A mismatched, revoked or out-of-period profile returns HTTP 409.
Profiles are created and reviewed by an independent NUERS administrator. A merchant cannot approve its own
original-source evidence. A profile is immutable; incorrect evidence requires revocation and replacement, not editing
an accepted original.
Mode is part of original content
Persist the chosen mode and profile ID in the original outbox payload. Do not change them while retrying an
accepted event. A source profile permits capture only; it does not authorize new NUERS originals or BIR
reporting.
In source_capture, keep the original receipt_number and occurred_at. NUERS does not allocate a new sequence.
In nuers_issuance, the submitted number must be the next authorized value; never renumber an ERP original
simply to pass that check.

Invoice versus collection
An order-created, cart-created or payment-authorized webhook is not automatically a finalized invoice. Map the

Calculation bucket

Ordinary 12% VAT; taxable base and VAT are separated.

review of the actual transaction. The API does not determine those facts from a product description.

Rounding order matters
The server rounds quantity x unit price to centavos, rounds each percentage discount to centavos, then extracts or
adds VAT per line. It sums the resulting lines. Do not calculate VAT once on an aggregate that can round differently.
quantity has up to four decimals; discount_pct has up to two decimals.
For a taxable inclusive line: base is the discounted inclusive amount / 1.12, rounded to centavos; VAT is the
remainder. For an exclusive line: VAT is 12% of the discounted base, rounded to centavos. All supplied line_total
and header totals must reconcile exactly.
Use gross_amount consistently
gross_amount is the final document total including VAT, before withholding. Avoid mixing the amount alias
with gross_amount; the exclusive-price alias represents the discounted pre-VAT subtotal. Do not send the
portal's integer-centavo prices to this pesos API.

Lost-response example
1. ERP commits invoice A and its original JSON to its durable outbox.
2. NUERS accepts A, creates the record and charges any eligible fee. The response is lost.
3. The worker cannot prove success, so A remains pending. It sends the same payload again.

fields or create a fresh ID to evade HTTP 409. Reconcile, then use the lawful correction process.
This is idempotent acceptance, not a promise of exactly-once network delivery. The connector uses at-least-once sending plus stable source
identity and verified durable acknowledgment.

A reliable delivery state machine
Contract: NUERS-ingestion-1 | Verified source snapshot: 18 October 2026

on source finalization:
    BEGIN source transaction
    save original invoice
    insert immutable outbox event, state=PENDING
    COMMIT
worker:
    claim oldest due event with a recoverable lease
    verify local payload hash
    send exact saved JSON with current scoped key
    if 200/201 and matching durable acknowledgment:
        BEGIN source transaction
        save NUERS inbox/receipt/transaction IDs
        set state=ACCEPTED, accepted_at=current time
        COMMIT
    else if 402:
        set state=FUNDING_REQUIRED; alert operator
    else if 401/403:

    else if 409/422/415/413:

    else if timeout/408/429/5xx/unverifiable 2xx:
        set state=PENDING; schedule bounded retry
    release lease; never delete the pending original
This is implementation pseudocode, not a NUERS endpoint. Recheck account/key policy after operational changes.
Stop the series on its first unaccepted event; unrelated permitted series can be scheduled separately.
Bounded backoff with jitter
A reasonable connector starting policy is a one-second base, doubling per attempt, capped at five minutes
with random jitter. Honor Retry-After when present. After a configured attempt/age threshold, alert an operator
and retain the original. These are example client settings, not a throughput SLA or legal deadline extension.
Poll or replay with a replacement key only when it belongs to the same merchant and original location. Do not change the event identity
during rotation. The local error-state names above are suggestions; the NUERS portal queue uses its own states.

1-100 items/event; 1-50 events/batch.
Shared network
300 API requests per minute per observed public IP; other apps/actions can share that
budget.
Authenticated key
Default 50,000/day; policy can set 100-1,000,000/day. Internal minute quota is 600, subject to
stricter network limits.
Batch route
Additional 10 requests/minute. Polling/status/wallet also use key/network quotas.
Daily rollover
Application calendar day, Asia/Manila in this deployment; use Retry-After where supplied.
Quota admission occurs before business validation, so authenticated rejected business requests can consume
budget. Matching replays avoid another sale fee but still use HTTP quotas. These controls are not measured
throughput or an uptime guarantee.
Funding policy
Read pricing from /wallet. The current threshold is PHP 500.00 per eligible primary sale; the published starting fee is
PHP 3.00 but future fees can change. Supplementary payments and accepted duplicate replays do not add another
primary-sale fee. A batch must fund all new eligible events or its new financial writes roll back.
Protect secrets and customer records
Use exact backend egress IP restrictions where suitable, encrypt queue backups, mask logs, and keep
MFA/passwords out of connectors. Never disable certificate verification. An operator using Manual Retry must
satisfy the same API key IP policy; arrange controlled access rather than removing safeguards casually.
