02 | SCOPE AND ARCHITECTURE
System purpose and boundaries
A merchant transaction platform with separate identity, financial, delivery and regulatory concerns.
NUERS receives merchant transaction events, records accepted financial data, maintains
electronic document views, tracks wallet charges and exposes status to merchant-owned ERP,
POS and e-commerce systems. Merchant and administration portals provide controlled access
to records, reviews, reports and integration settings.
Boundary
Technical meaning
Source capture
Preserves a copy of an original already issued by the merchant system,
including its number, issue date and source identity. It does not allocate a
second original invoice number.
NUERS issuance
Creates a new original only through the applicable issuance eligibility,
authorization and numbering controls. Account activation alone is not
issuance authority.
NUERS acceptance
A durable local result after validation and the financial database commit. A
network acknowledgement and a delivered email are separate states.
Government
transmission
Internal preparation and controlled delivery interfaces exist. The default
provider is blocked; no operational BIR transport or accreditation is asserted
here.
Architecture principles
One accepted business event produces one financial result; retries return the stored result
when the identity and content match.
Live and Sandbox use credential-derived environments. Synthetic tests must not debit real
wallets or become Live report entries.
Database commits precede external delivery. Merchant webhook and customer email
outcomes cannot roll back an accepted sale.
Every privileged operation is checked at the server boundary; a hidden or disabled browser
button is not an authorization control.
This manual describes software behavior and proposed operations. It is not a certificate of accreditation, a
penetration-test report, a hosting contract or an executed service-level agreement.

Sequence is simplified to emphasize commit ordering; all authentication and validation failures return before a

03 | END-TO-END PROCESSING
Idempotency and error recovery
The integration protocol distinguishes a rejected request from an unknown delivery outcome.
Outcome
Connector action
201 - accepted
Save NUERS record identifiers and mark the source event successful.
Acceptance follows durable recording.
200 - identical replay
Use the original result; do not count a new sale or add a second fee.
400 / 422 - invalid request
Show the validation reason to an authorized operator; correct the
rejected event according to the source-system workflow.
401 / 403 - identity or access
Check expiry, revocation, scopes, account eligibility and configured
restrictions. Do not expose the secret in logs.
402 - insufficient wallet
Show the reason and direct the merchant to fund the wallet. Retry the
same event after resolution.
404 - status not visible
Check business, branch and environment. A cross-environment lookup
must not reveal another record.
409 - conflicting identity
Stop automatic replay. Reconcile the original event and content; do not
invent a reference to bypass the conflict.
429 / transient 5xx / timeout
Use bounded exponential backoff with jitter. Preserve the event and
query or retry unchanged after an unknown outcome.
Stable source identity includes the merchant context, branch, source system and
event/document reference. The service also compares canonical content. A copied source
document keeps its original number and issue date; changing those fields is not a legitimate
duplicate-avoidance technique.
The batch intake supports 1-50 complete events in one branch context and is designed for
all-or-nothing acceptance. Apply request-size and item limits before transmission. A connector
must not interpret the failure of a batch as evidence that a separately submitted event failed.
I: schema NUERS-ingestion-1 and current integration contract. Exact field-level examples belong to the
merchant connection guide and OpenAPI file; release both with the same application revision.

05 | TRANSMISSION AND CALLBACKS
Merchant webhook protocol
Signed notifications provide asynchronous status; the receiver must still deduplicate.
The owner configures a public HTTPS callback for the appropriate environment. Endpoint
verification uses a challenge; a successful verification leaves it paused until activation.
Configured events include transaction.accepted, source.received, invoice.issued and
payment.recorded. Secrets are separate from API credentials and versioned.
Protocol / safeguard
Reviewed behavior
Signature
HMAC-SHA256 over timestamp + "." + event_id + "." + raw_body;
X-NUERS-Signature contains the v1= prefix.
Headers
X-NUERS-Event, X-NUERS-Timestamp, X-NUERS-Environment and
X-NUERS-Key-Version accompany the JSON event.
Destination
Public DNS hostname, HTTPS port 443, no credentials/query/fragment, no
NUERS self-callback. All resolved addresses checked against private/reserved
ranges.
Transport
DNS resolved again and pinned; certificate/hostname validation on; no proxy
or redirect fallback; 3-second connect and 8-second total timeout; response
limited to 16 KiB.
Durability
Encrypted body and SHA-256 content hash; leased attempts. Retry budget is
12 attempts within the ordinary one-day deadline, with exponential delay and
jitter.
Stop conditions
Redirects and selected permanent HTTP rejections dead-letter;
changed/revoked endpoint or account can cancel pending work.
The receiver should verify the signature against the exact raw request body, enforce an agreed
timestamp tolerance, compare signatures in constant time and persist the event ID before
acknowledging. Return 2xx after durable receipt, then process internally. Duplicate callback
delivery must be harmless.
I: current merchant webhook services. P/V: the merchant receiver and a real end-to-end delivery test.
Callback payloads intentionally omit customer details, monetary amounts, secrets and document images.

05 | TRANSMISSION AND CALLBACKS
Government transmission boundary
NUERS receipt, readiness and official acceptance must remain distinguishable.
The current merchant API exposes NUERS success or an error reason. Its accepted response
strips bir_status and related internal BIR preparation fields. This simplifies the connector
contract without converting a local success into a government acknowledgement.
Stage
Evidence and operational treatment
Local acceptance
Stored financial result and NUERS identifiers. Safe to report as recorded
by NUERS after success.
Internal preparation
Readiness model and source/authority checks; this is not a verified
government wire message.
Delivery eligibility
Current taxpayer, branch, environment, authorization, source coverage
and solution controls must pass.
Official transport
The reviewed default BlockedProvider returns not ready and refuses
send/inquiry. A verified adapter and credentials are required before
enabling a real path.
Official acknowledgement
Only an authentic provider response/inquiry can establish the relevant
external outcome. Never fabricate acknowledgements to clear a
dashboard.
Unknown outcome
Reconcile by authentic inquiry before replay. Preserve the job, evidence
and prior attempt history.
Operational release gate
A future transport release must identify the authoritative interface specification, mapping tests,
signing/certificate requirements, authorized endpoint, taxpayer scope and reporting obligations.
Review duplicates where source originals may already have been reported through another
system. Keep credentials out of screenshots and source control.
The delivery and reconciliation commands expose internal work and incident reminders. Their
existence does not prove a running scheduler or a successful external transmission. Operators
must inspect recorded outcomes and preserve the provider evidence.
V: accreditation, authority, live transport, service credentials and provider acknowledgements. This manual
makes no representation that these have been granted or independently verified.

Decision principles
Choose one authoritative primary database writer and a documented recovery site. Do not
distribute active writers across providers without an explicitly engineered consistency and
failover design. A lower-cost compute provider can be combined with independently managed
backups, but the team must own network, database, key and restore operations.
Complete procurement, privacy review, region restrictions, provider access terms, monitoring,
backup restoration and failover drills before declaring the proposed design operational. Provider
certifications or facility features do not automatically certify the NUERS workload.

08 | ENCRYPTION AND KEY MANAGEMENT
Key rotation and recovery runbook
Preserve decryptability while reducing exposure; never replace APP_KEY casually.
Phase
Procedure and evidence
1. Inventory
Identify data protected by the key: MFA seeds, private files, sensitive payloads,
endpoint secrets and mail recipients. Record current version references without
exposing values.
2. Prepare
Verify an encrypted backup and independent recovery path. Restrict access to
key material. Test rotation against a representative isolated copy and all
dependent services.
3. Introduce
Use a reviewed versioned-key rollout. Laravel supports previous application
keys, but effective configuration and every data format must be tested. Keep
old decryption available during transition.
4. Re-encrypt
Migrate data in bounded, restartable batches with audit evidence. Verify a
sample and aggregate counts. Avoid reading secrets into general application
logs.
5. Validate
Test document retrieval, MFA, callback signing, email rendering and restore
operations. Confirm new writes use the intended key version.
6. Retire
Retire an old key only after all required retained data and backups have a

destruction evidence.

If an application key may be exposed, treat confidentiality of all data protected by it as
potentially affected. Isolate the cause, preserve evidence, revoke compromised access and

custodians under the proposed policy. Test recovery without publishing the key or restoring
outbound delivery into an uncontrolled environment. Loss of a required decryption key can
make a technically intact backup unusable.

ceremony has already occurred.

09 | AUDIT, PRIVACY AND SECURE CHANGE
Audit integrity and evidence custody
A hash chain is tamper-evident evidence, not independent immutable storage by itself.
BirCompliance appends audit events under a locked chain head. The event hash includes the
previous hash, event name, subject, actor, serialized details and UTC timestamp. Integrity
verification recomputes the chain and compares the final head. This helps detect changes
relative to a trusted reference.
The checkpoint command verifies the chain and signs a checkpoint using a separately
configured HMAC key. Its local file is not automatically an offsite immutable record. An attacker
with sufficient database and application-key privileges could otherwise replace both records and
local evidence.
Evidence type
Handling baseline - proposed
Audit events
Restrict write permissions to controlled services; prohibit ordinary
edit/delete access; review gaps and failures.
Independent checkpoints
Export to a separate account/custodian, verify signatures and retention,
and test retrieval during recovery.
Security logs
Record event category, actor reference, environment, outcome, request
correlation and time; redact tokens, passwords, buyer details and
callback secrets.
Forensic copies
Capture source, acquisition time, collector, SHA-256, access history and

11 | INCIDENT RESPONSE PLAN
Financial integrity and outage
playbooks
Protect accepted records and prevent a recovery action from creating another incident.
IR-03: wallet or duplicate-transaction mismatch
Freeze the affected write path if continued processing risks further inconsistency. Preserve the
intake identity, canonical hash, acceptance result, transaction/receipt IDs, fee policy, wallet
entries and audit events. Compare the merchant source outbox to accepted NUERS records.
Determine whether the anomaly is a display/query issue, a rejected request, an unknown
outcome or an actual ledger discrepancy. Use a reviewed adjustment or corrective release; do
not patch posted balances directly.
IR-04: ransomware or suspected host compromise
Isolate the affected host and credentials without destroying volatile evidence. Stop untrusted
replication from overwriting clean recovery material. Identify the earliest trustworthy restore
point and independent keys/checkpoints. Rebuild from known artifacts in an isolated
environment, validate integrity, rotate exposed credentials and perform privacy review. A clean
antivirus result alone is insufficient recovery evidence.
IR-05: regional/provider outage or database failure
Declare impact, preserve available failure evidence and confirm whether the outage is
transient. Fence the old writer before standby promotion. Restore a compatible
database/object/key set, reconcile uncertain external side effects and verify balances,
sequences and audit chain. Switch traffic only after the authorized recovery decision, then
resume workers gradually.
IR-06: receipt email sent to the wrong recipient
Pause affected mail processing, preserve recipient source and delivery state, identify the
exposed document/data classes and prevent further copies. Assess whether a source input,
tenant boundary or rendering bug caused the event. Route to the privacy lead and correct the
cause before an authorized resend. SMTP acceptance does not prove recall is possible.
P: each playbook must name an owner, preserve a timeline, define a rollback/stop condition and capture
verification evidence. Do not use production financial writes as a diagnostic shortcut.

Incident and recovery evidence
forms
Use these field sets in the controlled operations system; do not place secrets in the record.
Incident record
Required fields
Identity
Incident ID; severity; commander; technical/security/privacy owners;
environment; detection time and timezone.
Impact
Affected services, tenants and data classes; first/last known occurrence;
confirmed facts; unknowns; business impact.
Timeline / evidence
Timestamped actions; request/event IDs; evidence location and hash;
custodian; access/transfer record.
Containment / recovery
Paused/revoked resources; decisions and approvers; restoration point;
verification results; residual risks.
Communication / close
Notification assessment and deadline; sent-message references; next
update; root cause; corrective actions and due dates.
Recovery exercise record
Required fields
Scope and source
Scenario; release/schema versions; backup IDs; database commit point;
object inventory; key version references.
Execution
Isolated destination and region; outbound delivery controls; operator;
start time; restore steps; errors.
Validation
Record counts/totals; wallet reconciliation; audit checkpoint; document
hashes; session/key revocation; sequence and pending-work checks.
Measured outcome
Source/recovered commit timestamps; actual RPO;
outage/restored-service timestamps; actual RTO; exceptions.
Approval
Independent reviewer; pass/fail basis; follow-up owners; next exercise
date; evidence retention location.
P: templates are ready for adoption, not populated proof of an incident or successful recovery. Keep any
populated forms in restricted storage and distribute only redacted summaries externally.

A successful local transaction, an issued original, a prepared internal model, a transmitted
message and an acknowledged external result are different states. Always identify the
boundary and evidence before using the word success in a report or service commitment.
Use the definitions consistently in merchant interfaces, operator runbooks, API documentation and incident
communications.
