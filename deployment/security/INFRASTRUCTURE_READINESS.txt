No size recommendation here establishes production capacity; size from measured peak
CPU/RAM, database growth, concurrent requests, working-set indexes and backup headroom.

Provisioning inputs: target host/IP/region; owner and billing approval; SSH access via
approved private key; provider console access; private network; monitoring destination;

Record package versions, OS security support, PHP modules, scheduler units, firewall,

Rehearsal on the new target:
 - Install only official supported packages, security updates and the reproducible NUERS
   release. Use explicit separate runtime and migration credentials; no DB port exposed.
 - Import an approved encrypted recovery copy into an isolated database. Preserve source
   schema, character set, collation, trigger semantics and time-zone handling. Inspect
   all 48 trigger definers; never import a nonexistent or overprivileged remote definer.
 - Reconcile row counts and integrity: receipts, transactions, wallets and wallet entries,

Controlled cutover:

 - Freeze writes and drains, capture final encrypted DB/objects and timestamp the last

C. OFFSITE BACKUP / RECOVERY
Provision storage in a separate account/failure domain and approved data region. Set
private access, versioning, retention and provider-side object lock where applicable.
Use a service credential limited to the NUERS encrypted-archive prefix, with no delete
or retention-bypass permission. Separate backup writer, recovery reader and key custody.
Do not keep the only APP_KEY/archive-key recovery copies on the production server.
Transfer keys through a separately approved secret manager/offline custody process;
do not include them in this repository, PDF, email attachment or archive upload.

Prepared tool: offsite-copy.py plus offsite.json.example. It is disabled by default and
not installed as a live scheduled transfer. Configure a root-owned mode-0600 rclone
profile for the approved destination only; TLS verification must remain enabled. A
named remote must be an actual independent provider/host, not a local folder alias.
The tool accepts one generated archive ID and its checksum, rejects plaintext envelopes
and unsafe destinations, copies without overwriting changed objects, and streams remote
encrypted bytes for SHA-256 comparison. The two local guard tests pass. Neither a real
provider transfer nor clean-host recovery has been tested. Client --immutable alone is
not proof of provider-side WORM/Object Lock.

After approved destination setup:
  python3 offsite-copy.py ARCHIVE_ID RECORDED_SHA256          (validate/plan only)
  python3 offsite-copy.py ARCHIVE_ID RECORDED_SHA256 --execute (encrypted copy/readback)
No APP_KEY, archive key, plaintext database or credential profile is uploaded by this tool.
Record remote object ID/version, retention, region, checksum and time. Then restore from
the REMOTE copy on a clean isolated host with separately retrieved keys; reconcile DB,
objects, audit and wallet state; exercise the application and measure recovery/data loss.
Until that succeeds, offsite recovery and production RTO/RPO remain unverified.
