CAUSE AND CHANGE
The previous sales report loaded every matching ledger row, performed source and payload validation per row, and grouped/paginated afterward in PHP. This could time out and leave the browser waiting.

The report now uses a rebuildable, indexed reporting projection. Financial and linked-payload evidence is validated in batches when source data changes. SQL calculates summaries and bounded groups; only the requested page (maximum 100 records) is hydrated. Revision-keyed caches share totals across page navigation. Near-end pagination reads from the nearer end. Selective text searches retain a bounded set of matching IDs. CSV streams in bounded chunks; the existing detailed PDF safety cap remains 500 records.

Twelve queue-only triggers invalidate source eligibility when linked payloads, transmissions, acknowledgments or original adjustment documents change. No source transaction, receipt, wallet or key is rewritten by these triggers. Missing projection eligibility fails with an explicit retry response instead of silently counting unvalidated rows.

The browser cancels superseded requests, avoids overlapping refreshes, has a 20-second timeout and displays an error with Retry. An initial failure displays unavailable values instead of fabricated zero totals.

MariaDB strict SQL mode required grouping by the projected label alias. This production compatibility issue was found during final UI checks and corrected in release .2. All Daily, Monthly, Business, Transaction Type, Payment Method and Branch group queries then passed.

LIMITS
Uncached substring searches still scan text fields and can be slower than indexed browsing (10.78 seconds in the final lab run). Broad unfiltered aggregate cache misses scale with matching rows. The benchmark does not establish a production SLA or performance under simultaneous million-row imports and many concurrent report users. Reconciliation's separate legacy inspection path was not rewritten in this change. No claim is made that every system endpoint was benchmarked.
