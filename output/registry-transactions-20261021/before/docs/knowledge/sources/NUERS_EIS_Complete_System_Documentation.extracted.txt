2. Platform architecture and transaction lifecycle
Flow: POS / ERP / e-commerce / NUERS Portal -> WAF + authenticated tenant API -> taxpayer eligibility + PTI/PTT gate ->
canonical invoice validation -> immutable invoice ledger and transactional outbox -> durable queue -> BIR EIS adapter ->
acknowledgment storage -> reconciliation -> taxpayer portal / reports / audit.
State machine: Draft -> Validated -> Issued -> Queued -> Transmitting -> Submitted -> Acknowledged / Rejected /
Uncertain. Acknowledged means confirmed by an authoritative BIR response, not merely HTTP 200. Uncertain requires
inquiry and reconciliation before any replay. Corrections are controlled events, never silent mutation of issued invoices.
Idempotency: each source has stable source ID + tenant + branch + document type; requests with the same idempotency
key return the original result. Persist invoice and outbox atomically. Queue consumers must tolerate duplicate delivery.
Deadline management: submit in real/near-real time; track transaction time, attempt time, BIR acknowledgment and
three-calendar-day compliance deadlines. Escalate before breach, and preserve evidence of BIR outages and recovery.

8. Detailed BIR transmission workflow
1. Select issued eligible documents. 2. Validate taxpayer and interface authorization. 3. Serialize to BIR-approved schema. 4.
Commit delivery intent and hash. 5. Submit through officially provisioned secure interface. 6. Record request/response and
latency. 7. Parse authoritative acceptance/rejection. 8. Update state and reconciliation. 9. On timeout, mark uncertain and
inquire before resubmission. 10. Preserve all attempts and notify owners on deadline risk.
Transmission modals: Batch details with count and scope; retry confirmation with last response; response viewer with
redacted secrets; incident/outage declaration; manual reconciliation approval. The official endpoint, response codes and
payload schema remain pending authoritative BIR documentation.
9. Security, performance and disaster recovery
Proposed infrastructure: two 64-physical-core/128-GB Web nodes; two similarly sized database nodes plus independent
quorum/fencing mechanism; three 64-core/128-GB object-storage nodes. Separate durable queue, monitoring, immutable
backups and offsite DR. Two DB nodes alone are insufficient for quorum-safe automatic promotion.
Target load: 1 million transactions/hour (~278 TPS average), with burst testing to 2,000 TPS; these are design targets, not
proven capacity. Test complete invoice issuance, persistence, acknowledgments, audit and document delivery. Provide WAF,
TLS, encryption at rest, MFA, access controls, security review, penetration testing and monitored incident response.
10. Production acceptance gates
Gate A: Confirm ESP eligibility and solution-specific accreditation path. Gate B: Confirm taxpayer PTI/PTT authority and
applicable EIS requirements. Gate C: Obtain official interface specifications and complete conformance tests. Gate D:
Validate accounting/tax rules and invoice numbering. Gate E: Complete load, security, failover, backup/restore, privacy and
interoperability tests. Gate F: Document BIR-supervised tests and approvals before live taxpayer production.
Acceptance cases: 1M/hour sustained, one web node loss, database promotion without lost acknowledged writes, one
storage node failure, duplicate source replay, BIR 5xx/timeouts, acknowledgment mismatch, near-deadline queue, taxpayer
permit expiry, tenant cross-access attempt, manual outage invoice linkage, full restore, and structured export on termination.
