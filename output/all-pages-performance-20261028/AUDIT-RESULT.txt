CHANGES
- 98 page components load on demand; initial main JavaScript reduced from 2,384,430 to 540,878 bytes (about 77%). Navigation remains available during lazy-page loading.
- Transaction, reconciliation, EIS and merchant registers select bounded IDs before loading detail rows. Stable ordering and reverse-end pagination reduce deep final-page cost.
- Reconciliation evidence is derived when source records change. Foreground lists no longer decode all historical financial payloads.
- Revision-aware summary caches and covering indexes reduce repeat aggregation. Broad merchant sales reports avoid random index lookups when most of the table is needed.
- Default merchant counters use narrow indexes; detailed delivery evidence and restricted team scopes retain their existing authorized query.
- Large audit journals use scheduled full-chain verification, with checked time and honest pending/failed status in the UI.

LIMITS
- This is not a production concurrency SLA or proof that every possible filter/detail route is instant at arbitrary scale.
- Large uncached aggregates still take several seconds (up to about 8 seconds in the measured merchant paths). Cached results are fast; writes invalidate financial summaries before subsequent reads.
- Broad contains searches and deep middle-page offsets can cost more. Narrow date/merchant filters remain useful.
- Million-row EIS timing used no delivery jobs. Delivery-history joins keep the full evidence path and require a separate large-scale delivery-history benchmark before claiming the same timings.
- Live merchant browser sign-in was not impersonated; merchant UI checks used synthetic accounts, with production read-only scope checks and tenant-security tests.
- Existing generic operational-readiness pages remain their existing functionality. BIR connectivity, off-server DR and other infrastructure readiness were outside this performance release.
