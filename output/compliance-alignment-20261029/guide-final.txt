01 / SET UP
From verified account to API key
01 Sign in as the registered business owner / Merchant Admin and complete the login verification. Open Business
Profile and confirm that the business is Active and its taxpayer details are correct.
02 Open Merchant > API Integration. Choose Generate New API Key, enter a clear name such as ERP Connector,
and choose Sandbox for initial testing.
03 Copy the API key when it is shown. Store it in your server's secret manager. It is shown once; the portal does not
reveal the original secret again.
04 Copy the assigned source_profile_id, source_system and branch_code from the connection / ERP configuration
or Source Profiles tab.
05 Use the wallet endpoint on page 7 to check authentication and confirm the environment and assigned business
context. Then submit a synthetic Sandbox event.
06 After completing the checklist on page 34, generate a separate Live key and use the Live connection
configuration for actual transactions.
Automatic business connection
An active, verified merchant receives its owned-system connection automatically. There is no second source
approval and no merchant Branches / Terminals form to complete before creating this connection.
If the button is disabled: enter a key name, check that you are the registered owner, then use Refresh Status or reload once. An
already-active account does not need another approval. If it remains blocked, send a redacted screenshot and time to Submit a
Request. Never include the secret key.

Environment rules for your connector
01 Use separate secret-store entries, outbox queues, response stores and webhook configuration for each
environment. The environment belongs to the API key; a JSON flag cannot switch it.

source profile covers the original date or historical seller identity. Check the assigned Live profile and an
authorized real pilot before cutover.

01 / SET UP
Authentication and credential care
X-NUERS-API-Key: <your server-held API key>
Content-Type: application/json
Accept: application/json
Use the header above on every API call. The API key is itself the secret credential; a separate public key, private
key pair or token exchange is not required for this connection.
Control
Merchant action
Scopes
transactions:write submits events. transactions:read reads status and wallet. Manual retry needs
both.
IP restrictions
Use Edit Key Policy to allow the connector's exact public IPv4 / IPv6 egress addresses. Include
your failover egress before switching.
Expiry
Generated keys expire after 90 days. Track the displayed expiry and rotate before it.
Daily quota
Default Live key: 50,000 requests/day. Sandbox: 5,000/day. Check the key's current policy. Other
shared limits also apply.
Owner access
Credential changes require the registered owner's verified login. Keep MFA enabled.
Lost key
Generate a replacement. The original secret cannot be recovered from the masked display.
Safe rotation
Create the replacement in the same environment and business context. Update the server secret, verify
wallet/status access, then revoke the old key. Keep the original event IDs and JSON when retrying queued events.
Revocation is permanent.
Secrets stay on the server
Do not embed API keys in browser code, mobile apps, URLs, screenshots, support tickets, webhook bodies or
logs. Keep HTTPS certificate verification enabled and redact authentication headers.

Reconciliation rules
01 Choose one price basis for the whole document with vat_inclusive. Express unit_price in that basis.
02 Calculate each line using quantity, price and applicable discount; round currency amounts to centavos. Calculate
each line's VAT, then sum the lines.
03 Send gross_amount as the final total including any VAT and after discounts, before withholding. The server
recalculates and rejects a mismatch.
04 Compare the returned calculation to your original source document. Do not silently alter an already-issued
original to force a match.
Do not pre-discount twice
For a statutory benefit, supply the original pre-benefit unit_price and mark eligible lines. NUERS applies the
category calculation. A pre-discounted price plus benefit_eligible would apply the benefit again.
Use integer centavos or a decimal library in your own accounting code. Binary floating-point addition should not determine monetary
equality. The accepted document total is capped at PHP 10 billion.

cURL and Postman quick start
Submit one saved JSON file
curl --silent --show-error \
  --connect-timeout 10 --max-time 45 \
  --request POST \
  "https://nuers.net/api/integrations/transactions" \
  --header "X-NUERS-API-Key: ${NUERS_API_KEY}" \
  --header "Content-Type: application/json" \
  --header "Accept: application/json" \
  --data-binary @event.json \
  --output response.json \
  --write-out 'HTTP %{http_code}\n' 
event.json must contain a complete event. Save its exact content in your outbox first. A network timeout leaves the
result unknown; keep the event pending and retry unchanged. Inspect response.json and the HTTP status together.
Postman setup
01 Create separate private Sandbox and Live environments. Set base_url to the API base and api_key as a secret
variable. Do not export or share its current value.
02 Create a POST request to {{base_url}}. Add X-NUERS-API-Key: {{api_key}}, Content-Type: application/json and
Accept: application/json.
03 Choose Body > raw > JSON. Paste the complete event with your assigned identifiers, then send in Sandbox.
04 Verify HTTP 201 and status: durably_recorded. Save id. Repeat the same request and expect HTTP 200 with
duplicate: true and the same IDs.
Development tool, not the delivery queue
Postman and cURL help inspect a request. Your production connector still needs durable storage, controlled
retries and response reconciliation. Avoid verbose command output that exposes authentication headers.

04 / SENDER CODE
Node.js: one controlled send
Node.js 20+ example. The caller supplies the exact JSON already saved in its durable outbox. This function
performs one attempt and returns an acknowledgement only after checking identity and environment.
export async function sendNuers(savedJson) {
  const event = JSON.parse(savedJson);
  const key = process.env.NUERS_API_KEY;
  const env = process.env.NUERS_ENVIRONMENT;
  if (!key || !['live', 'sandbox'].includes(env)) {
    throw new Error('Missing private connector configuration');
  }
  const url =
    'https://nuers.net/api/integrations/transactions';
  const res = await fetch(url, {
    method: 'POST', redirect: 'error',
    signal: AbortSignal.timeout(45000),
    headers: {
      'X-NUERS-API-Key': key,
      'Content-Type': 'application/json',
      'Accept': 'application/json'
    },
    body: savedJson
  });
  const body = await res.json().catch(() => null);
  const accepted = res.status === 201 ||
    (res.status === 200 && body?.duplicate === true);
  const valid = accepted && body?.id && body?.receipt_id &&
    body?.transaction_id && body.environment === env &&
    body.status === 'durably_recorded' &&
    body.nuers_status === 'success' &&
    body.source_event_id === event.source_event_id &&
    body.external_reference === event.external_reference;
  if (!valid) {
    const err = new Error('NUERS response needs review/retry');
    err.status = res.status;
    err.retryAfter = res.headers.get('retry-after');
    // Redact personal data before logging field-level errors.
    throw err;
  }
  return body; // Caller commits IDs + delivered state locally.
}
A thrown network/parse error must leave the outbox pending. Handle HTTP statuses using page 32. Store the returned IDs and
delivered state atomically. Do not print savedJson or the API key.

PHP: request and transport handling
PHP 8.2+ with cURL. This is the first half of a single function; continue directly with page 19. It sends the JSON
string already stored in your outbox.
<?php
function sendNuers(string $savedJson): array
{
    $event = json_decode($savedJson, true, 64,
        JSON_THROW_ON_ERROR);
    $key = getenv('NUERS_API_KEY');
    $env = getenv('NUERS_ENVIRONMENT');
    if (!$key || !in_array($env, ['live', 'sandbox'], true)) {
        throw new RuntimeException('Missing connector config');
    }
    $retryAfter = null;
    $ch = curl_init(
        'https://nuers.net/api/integrations/transactions'
    );
    curl_setopt_array($ch, [
        CURLOPT_POST => true,
        CURLOPT_POSTFIELDS => $savedJson,
        CURLOPT_RETURNTRANSFER => true,
        CURLOPT_CONNECTTIMEOUT => 10,
        CURLOPT_TIMEOUT => 45,
        CURLOPT_FOLLOWLOCATION => false,
        CURLOPT_SSL_VERIFYPEER => true,
        CURLOPT_SSL_VERIFYHOST => 2,
        CURLOPT_HTTPHEADER => [
            'X-NUERS-API-Key: '.$key,
            'Content-Type: application/json',
            'Accept: application/json',
        ],
        CURLOPT_HEADERFUNCTION =>
            function ($ch, $line) use (&$retryAfter) {
                if (stripos($line, 'Retry-After:') === 0) {
                    $retryAfter = trim(substr($line, 12));
                }
                return strlen($line);
            },
    ]);
    $raw = curl_exec($ch);
    $status = curl_getinfo($ch, CURLINFO_RESPONSE_CODE);
    curl_close($ch);
    if ($raw === false) {
        throw new RuntimeException('Transport outcome unknown');
    }

07 / RECEIVER CODE
PHP signature-verification core
Call this before your business logic. The HTTP adapter must reject duplicate security headers and supply
lower-case header names, the raw body and private receiver settings.
<?php
function verifyNuers(string $raw, array $h, array $cfg): array
{
    $id = $h['x-nuers-event'] ?? '';
    $ts = $h['x-nuers-timestamp'] ?? '';
    $sig = $h['x-nuers-signature'] ?? '';
    if (strlen($raw) > 65536 ||
        !preg_match('/^[a-f0-9-]{36}$/D', $id) ||
        !ctype_digit($ts) || strlen($ts) > 12 ||
        abs(time() - (int)$ts) > 300 ||
        !preg_match('/^v1=[a-f0-9]{64}$/D', $sig) ||
        ($h['x-nuers-environment'] ?? '') !== $cfg['environment'] ||
        ($h['x-nuers-key-version'] ?? '') !== $cfg['key_version']) {
        throw new RuntimeException('Invalid webhook headers');
    }
    $mac = hash_hmac('sha256', $ts.'.'.$id.'.'.$raw, $cfg['secret']);
    if (!hash_equals($mac, substr($sig, 3))) {
        throw new RuntimeException('Invalid webhook signature');
    }
    $event = json_decode($raw, true, 32, JSON_THROW_ON_ERROR);
    if (($event['id'] ?? null) !== $id ||
        ($event['environment'] ?? null) !== $cfg['environment'] ||
        ($event['merchant_id'] ?? null) !== $cfg['merchant_id']) {
        throw new RuntimeException('Unexpected webhook identity');
    }
    return $event;
}
cfg contains secret, key_version as a string, environment and merchant_id. Map verification failures to HTTP 401;
do not process the body. Validate the event type, handle signed challenges, then apply the inbox rules on page 31.
Complete the HTTP route
Read php://input once, verifyNuers first, then handle the signed challenge or commit the business event to
your inbox. Return JSON with Content-Type: application/json. Do not return 2xx before persistence succeeds.

10 / MANUAL DISCOUNTS
Amount or percentage, invoice or line
Send original unit prices before discount. Add the following object at the top level to discount the whole invoice, or
inside one items[] entry to discount that line only.
"manual_discount": {
  "type": "amount",
  "value": "112.00",
  "reason": "Loyalty discount"
}
Field
Accepted input
type
amount for a fixed PHP amount, or percentage for 0-100%.
value
Non-negative; at most two decimals. Use a two-decimal string. Amount cannot exceed the original
line/document price.
reason
Required non-blank text, maximum 500 characters. Record the actual discount reason.
One VAT-inclusive item: PHP1,120.00
Discount method
Expected result
amount: 112.00
Manual discount 112.00; VATable base 900.00; VAT 108.00; gross_amount 1008.00.
percentage: 10.00
Same result. Existing items[].discount_pct: 10 also remains supported.
With vat_inclusive=true, discount amounts include VAT. With false, they reduce the pre-VAT price before VAT is added. A fixed line
discount applies to the whole quantity extension, not separately to every unit. VAT follows the recorded tax type of each discounted line.
Keep totals consistent
gross_amount is the final discounted total including VAT and before withholding. Do not pre-discount
unit_price and also send manual_discount. Invalid values or inconsistent totals return HTTP 422 before
financial records are committed.

10 / MANUAL DISCOUNTS
Allocation, reconciliation and reporting
01 Choose either one document discount or line discounts. A document discount cannot be combined with any line
discount or sales_benefit.
02 Document discounts allocate proportionally by each original line extension. NUERS uses integer centavos and
distributes leftover centavos to the largest fractional shares; original line order breaks ties. Use per-line fixed
amounts if your ERP uses a different allocation.
03 A line manual_discount cannot be combined with non-zero discount_pct or a statutory-eligible line. A basket may
have statutory-eligible items and separate non-eligible lines with manual discounts.
04 Compare calculation.manual_discount_amount, discount_amount (manual plus statutory),
statutory_discount_amount, VAT buckets and gross_amount to the original invoice. Gross totals already contain the
reduction; do not subtract it again.
Where
What is recorded
API response / source
record
Manual and statutory totals separately; line discount_reason plus discount_pct or
fixed_discount_amount in PHP. fixed_discount_amount is a response field, not a request input.
Merchant and admin
records
Manual Discount is shown separately from Statutory Discount and VAT Adjustment. Filtered CSV,
sales XLSX/PDF and document copies retain the breakdown.
Sandbox
Same validation and discount calculation; test records stay isolated and do not debit the Live
wallet.
Wallet / retries
Fee eligibility uses final discounted gross. Identical retries have no second charge; changing
discount or reason under an accepted identity returns 409.
Preserve the original
These fields record an ordinary discount reflected at sale time. Later conditional rebates require the
appropriate correction workflow. Existing accepted documents are not silently changed to add missing
discount details.
Tax reference: BIR RR 16-2005, section 4.106-9, addresses invoiced at-sale discounts for goods. Product eligibility and the applicable
tax basis remain the responsibility of the merchant. BIR published regulation.

11 / CONNECTOR SALES DASHBOARD
Show a truthful NUERS status
Every ERP, POS or e-commerce sales row must show NUERS Status, failure reason, environment, NUERS
reference and last attempt. Show Success only after a valid 201 or 200 duplicate acknowledgement with matching
source_event_id, external_reference and environment, non-empty id/transaction_id/receipt_id,
status=durably_recorded and nuers_status=success. Persist these identifiers atomically with the local outbox
acknowledgement.
Dashboard state
When to display it
Pending
The local sale is saved but has not yet received a valid NUERS acknowledgement.
Success
Matching acknowledgement with nuers_status=success and status=durably_recorded. Store all
returned NUERS IDs.
Error + reason
A known rejection. Show error.reason and relevant field messages. Keep the source sale for
correction or funding.
Pending confirmation
Timeout, malformed response or error.outcome=unknown. Retry the identical event; never create
a replacement identity.
Show Error plus error.reason and applicable errors field messages for a rejected request. Keep the original sale
locally. 402 requires wallet funding; 401/403 require credential or permission correction; 409 requires reconciliation;
422 requires mapping correction. For timeouts, invalid JSON, malformed 2xx or error.outcome=unknown, show
Pending confirmation and retry the identical original event. Honor Retry-After and bounded backoff for 429/5xx.
Never render server messages as HTML or expose credentials to the customer.
NUERS status in the sales row
Merchant transaction, batch and wallet responses do not expose bir_acceptance, bir_connection, bir_status or
internal preparation blockers. Display NUERS status in the connector. NUERS Success confirms platform
recording; it does not assert government acceptance.
Download the small connector UI adapter from https://nuers.net/guides/NUERS-Transaction-Status.mjs. Use it in your backend with the
saved source event and configured environment. Render messages as plain text. Your ERP/POS developer must connect these fields to
its own sales dashboard.

12 / CUSTOMER E-RECEIPTS
Map checkout email and saved branding
"customer_name": "SAMPLE Customer",
"customer_email": "customer@example.test"
Optional customer_email: one valid checkout email address, maximum 254 characters. Omit or send null when
absent. Map the checkout email explicitly; NUERS does not scan arbitrary payload fields. Invalid addresses return
422 before acceptance. Never use a customer address as an API credential.
A newly accepted Live event containing customer_email queues one customer PDF email in the same database
transaction. Exact retries return the same record and do not queue another email or fee. Failed/rolled-back events
queue no email. Sandbox always returns suppressed_sandbox and never emails customers. Existing transactions
are not emailed retroactively.
Use the merchant receipt design
Email attachments use the same receipt renderer and E-Receipt Logo saved under Merchant Invoice Settings →
Logo and Branding. This logo is independent from the Business Profile Picture; both uploads save immediately
without administrator approval. Original seller identity, lines, taxes, discounts and totals remain the recorded
snapshot. Save branding before the email worker renders the PDF; changes affect subsequent renders and cannot
recall an already sent attachment.
01 Merchant opens Invoice Settings, saves the dedicated E-Receipt Logo, colors, layout, footer and receipt
preferences.
02 Connector commits the customer email with the finalized source payload and sends it with the same immutable
event identity.
03 NUERS commits the sale and encrypted email job together, then returns Success plus
customer_receipt.status=queued.
04 The email worker renders the same merchant document as a PDF attachment and sends it through configured
platform SMTP.
One copy per accepted event
Keep customer_email unchanged on an identical retry. Changing it under an already accepted source identity
returns 409. Use the merchant document Send Copy action for a separately requested copy; do not create
another sale.

12 / CUSTOMER EMAIL OPERATIONS
Track delivery independently
customer_receipt.status
Meaning
not_requested
No checkout email supplied.
suppressed_sandbox
No customer email is sent in Sandbox.
queued / preparing / sending
Asynchronous work is waiting or in progress.
smtp_accepted
SMTP accepted the message; inbox delivery is not confirmed.
failed / expired / cancelled
Mail preparation, queue lifetime or account/document eligibility prevented sending.
uncertain
SMTP or worker outcome is unknown. Investigate before a manual resend.
Poll GET status_url with the same environment and transactions:read scope for customer_receipt.status and
reason. States: not_requested, suppressed_sandbox, queued, preparing, sending, smtp_accepted, failed,
uncertain, expired, cancelled. smtp_accepted means the SMTP server accepted the message, not confirmed inbox
delivery. Email failures never change a successfully recorded sale to Error. Do not retry the sale to resend mail; use
the merchant document Send Copy action after investigating an uncertain delivery.
Connector acceptance checklist
01 Show NUERS Status, environment, reference, last attempt and the error reason on every sales row.
02 Use synthetic addresses and separate Sandbox keys during mapping tests. Sandbox will not send test mail.
03 Test missing/invalid email, retry deduplication, batch rollback and branded PDF output in isolated fixtures.
04 Confirm the production email worker and SMTP configuration. Monitor delivery history; do not claim delivered
when only smtp_accepted is known.
Use the public API reference, this PDF and the merchant connection guide from the same release: 2026-10-29.compliance-operations.
Existing records are not emailed retroactively.

13 / WITHHOLDING & CORRECTIONS
Buyer-confirmed CWT
For buyer-confirmed CWT, send withholding_tax in PHP and withholding_basis_reference. Send
withholding_details with withholding_agent=true, classification, atc (two uppercase letters and three digits), rate
(percentage), base, amount and evidence_reference. Decimal money fields have at most two decimals. amount
must equal withholding_tax and rounded base × rate / 100. CWT reduces net_payable; gross_amount, sales, VAT
and the wallet fee basis stay unchanged. Existing amount-and-basis integrations remain supported; use the
structured buyer confirmation for new mappings.
{
  "withholding_tax": "10.00",
  "withholding_basis_reference": "BUYER-CONFIRMATION-001",
  "withholding_details": {
    "withholding_agent": true,
    "classification": "Buyer-confirmed withholding agent",
    "atc": "WC160",
    "rate": "1.00",
    "base": "1000.00",
    "amount": "10.00",
    "evidence_reference": "BUYER-CONFIRMATION-001"
  }
}
Example only
ATC and rate are illustrative. The buyer/payor must determine the applicable classification and rate. A PHP
1,120 invoice with PHP 10 CWT still records PHP 1,120 gross and PHP 120 VAT; net payable is PHP 1,110.

13 / WITHHOLDING & CORRECTIONS
Preserve the original
For CWT supplied or corrected after issuance, open Merchant → Compliance Operations → CWT adjustment
memos. Select the issued original and record buyer/payor confirmation. Issuing a registered credit memo requires
current authority and a credit-memo series. The original stays unchanged; sales and VAT adjustments are zero.
Subsequent corrections reference the current CWT amount, with stale drafts rejected.
For an increase, issue an additional electronic invoice referencing the original; for a decrease, use a credit memo.
The native merchant form does not create debit memos for new adjustments. Original records remain immutable.
The intake API does not accept credit-memo document types; use the controlled merchant workflow for a
NUERS-issued adjustment.
01 Open Compliance Operations and choose CWT adjustment memos.
02 Select the original invoice; provide buyer-confirmed classification, ATC, rate, base, amount and evidence.
03 Review the draft. Official issuance requires verified authority and an active credit-memo series.
04 Download the issued memo and retain the original invoice. Later corrections use the latest issued CWT
adjustment.

14 / OUTAGE RECOVERY
Authorized manual invoices
Record an outage and its authorized manual invoices under Merchant → Compliance Operations, then record
verified restoration. On a replacement Live invoice, send manual_recovery_id from that register and the original
manual number in manual_invoice_number. The replacement must match merchant, branch, buyer and gross
amount, explicitly reference the manual invoice and be dated after restoration. One manual invoice links to one
replacement. A mismatch rolls back the new event and fee. Sandbox cannot link Live recovery records. The register
tracks the three-calendar-day recovery deadline; it does not issue manual authority or claim BIR transmission.
{
  "manual_recovery_id": "00000000-0000-4000-8000-000000000002",
  "manual_invoice_number": "SAMPLE-MANUAL-001"
}
01 Record the outage and retain its evidence.
02 Register each authorized manual invoice with its original number, branch, buyer, date, gross amount and
authority reference.
03 Record verified service restoration. Track the replacement deadline shown in the register.
04 Send the replacement from your owned system with the recovery fields and matching original identity; preserve
its acknowledgement.
05 Review unreconciled manual invoices. A retry must use the identical original event; a second replacement is
rejected.

15 / PLATFORM CONTROLS
Readiness and fee invoices
Live storage intake remains available while ESP accreditation enforcement is prepared but disabled. This is an
operational setting, not a statement of BIR authorization. Official NUERS issuance and BIR transmission retain
separate authority checks.
NUERS service-fee statements use posted wallet debits and cannot bill a debit twice. An administrator prepares the
billing period. The merchant can review and download the statement under Compliance Operations. Official service
invoices require a separate registered NUERS billing entity, verified issuance authority and an active invoice series.
Preparing or issuing a fee document does not debit the merchant wallet again.
External evidence remains separate
BIR credentials and transmission, actual accreditation, independent security certifications and production
disaster-recovery evidence cannot be replaced by local software tests. Your records continue to be available
under the current approved operational scope.
