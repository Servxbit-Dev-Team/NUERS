## Main risks and decisions

1. **Containment vs compatibility:** centralized policies will expose UI/features that relied on unguarded endpoints. Test every alias/role and explicitly mark unavailable functionality; do not retain insecure fallbacks for convenience.
2. **Evidence migration:** imported records do not become approved by adding a default branch, permit or recalculated amount. Flag source review, require original basis and use lawful corrections. User has no approvals/evidence yet; no new request for secrets is necessary.
3. **Regulatory uncertainty:** exact BIR contract and taxpayer applicability remain outside repository proof. Do not toggle implementation flags, treat template codes B1-B6 as official protocol codes, or use a guessed endpoint.
4. **Idempotency migration:** existing merchant+reference uniqueness must be reconciled before widening the namespace; never permit repeat imports to create a second legal sale. Preserve old keys/hash history.
5. **External uncertainty:** provider timeouts and worker death require inquiry; standard retries can duplicate delivery. Provider-side duplicate semantics must be verified, not invented.
6. **Performance tradeoffs:** global audit-head and merchant locks protect integrity but may serialize writes; measure before partitioning. Avoid replicas for sequence/authority checks that require fresh consistency.
7. **Keys and backups:** app-key rotation can render old preparation payloads unreadable if custody/migration is mishandled. Backup restore must include keys and regulated objects under independent access controls.
8. **Availability vs rights:** suspension/unpaid fees must not prevent legally authorized taxpayer retrieval/portability. Define narrowly allowed suspended-account actions instead of removing all access indiscriminately.
